# WSCD PostgreSQL Schema and Service Specification

## Purpose

This document is the technical follow-up to:

- [web-migration-plan.md](/Users/rafakwolf/Developer/p/wscd/docs/web-migration-plan.md)

It defines the recommended target shape for:

- PostgreSQL schema
- naming conventions
- enums and statuses
- indexes and constraints
- derived calculations
- transactional service workflows

This is intended to be implementation-ready enough for backend development, while still allowing small naming adjustments during coding.

## Scope of This Spec

This specification covers the recommended target model for the web rewrite MVP and near-MVP.

Included:

- organization-aware schema
- catalog entities

- finance
- settings
- reports support

Excluded:

- auth provider schema
- frontend component design
- infrastructure deployment
- final ORM/tool choice
- mandatory legacy data import planning

## Design Principles

### 1. Multi-organization by design

Even if the first deployment is for one business, the schema should support more than one organization from day 1.

Reason:

- low extra cost now
- much harder to retrofit later
- clean ownership boundaries

### 2. Explicit transactional workflows

The legacy Firebird system hides critical business logic in procedures and triggers.

The new system should move these rules into explicit backend service operations.

### 3. Preserve history where possible

The Delphi app often deletes related records when canceling operations.

The web version should prefer:

- status transitions
- reversals
- explicit source references

instead of destructive deletion.

### 4. Use PostgreSQL-native types

Do not mimic Firebird semantics literally.

Use:

- `bigint` or `integer` identities
- `boolean`
- `numeric(14,2)` for money
- `date` for business dates
- `timestamptz` for audit timestamps
- `text` for freeform notes

### 5. Derived fields should be derived

Do not persist values that are naturally derived unless there is a strong reporting/performance reason.

Examples:

- delay days
- stock value
- receivable/payable totals with interest

## Naming Conventions

### Schema

Use the default `public` schema unless a strong need appears later.

### Table names

Use plural snake_case table names.

Examples:

- `customers`
- `sales`
- `sale_items`
- `accounts_receivable`

### Columns

Use snake_case.

Examples:

- `organization_id`
- `customer_id`
- `sale_date`
- `total_amount`

### Primary keys

Every business table should have:

- `id bigint generated by default as identity primary key`

### Foreign keys

Use `<table>_id`.

Examples:

- `customer_id`
- `purchase_id`
- `cash_account_id`

### Timestamps

Standard fields:

- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`

For immutable ledger-style tables, `updated_at` can be omitted.

## Recommended Enums

PostgreSQL enums are suitable here because the business statuses are stable.

```sql
create type party_type as enum ('individual', 'company');
create type cash_entry_type as enum ('credit', 'debit');
create type receivable_origin_type as enum ('sale', 'manual', 'other');
create type payable_origin_type as enum ('purchase', 'manual', 'other');
create type quotation_status as enum ('draft', 'sent', 'approved', 'rejected', 'converted', 'expired');
create type purchase_status as enum ('draft', 'posted', 'completed', 'canceled');
create type sale_status as enum ('draft', 'posted', 'completed', 'canceled');
create type settlement_method as enum ('cash', 'pix', 'card', 'bank_transfer', 'check', 'credit_account', 'other');
create type loss_reason as enum ('expiration', 'damage', 'internal_use', 'adjustment', 'other');
```

If the team prefers more flexibility, these can be converted into `text + check constraint`.

## Core Shared Tables

### organizations

Represents a business/workspace that owns all ERP records.

```sql
create table organizations (
  id bigint generated by default as identity primary key,
  name text not null,
  slug text unique,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

### users and memberships

Auth is out of scope, but application ownership still needs a bridge between external auth and organization membership.

Minimal internal structure:

```sql
create table app_users (
  id bigint generated by default as identity primary key,
  external_auth_id text not null unique,
  email text,
  full_name text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table organization_memberships (
  id bigint generated by default as identity primary key,
  organization_id bigint not null references organizations(id) on delete cascade,
  app_user_id bigint not null references app_users(id) on delete cascade,
  role text not null default 'owner',
  created_at timestamptz not null default now(),
  unique (organization_id, app_user_id)
);
```

If you want to stay even leaner, this can be deferred until auth is wired.

Derived values:

- `delay_days`
- `interest_amount`
- `total_amount`
- `total_received_amount`

Recommended formula:

```text
delay_days =
  if is_received and receipt_date > due_date => receipt_date - due_date
  else if not is_received and current_date > due_date => current_date - due_date
  else 0

interest_amount =
  principal_amount * interest_rate * delay_days / 100 / 30

total_amount =
  principal_amount + interest_amount - discount_amount

total_received_amount =
  amount_received + interest_received
```

## SQL Views Recommended for Reporting

These are optional but useful.

### v_product_stock

```sql
create view v_product_stock as
select
  p.id,
  p.organization_id,
  p.name,
  p.barcode,
  p.current_stock,
  p.minimum_stock,
  p.cost_price,
  (p.current_stock * p.cost_price) as stock_value,
  (p.current_stock <= p.minimum_stock) as is_below_minimum
from products p;
```

### v_accounts_receivable_summary

```sql
create view v_accounts_receivable_summary as
select
  ar.*,
  case
    when ar.is_received and ar.receipt_date > ar.due_date then (ar.receipt_date - ar.due_date)
    when not ar.is_received and current_date > ar.due_date then (current_date - ar.due_date)
    else 0
  end as delay_days
from accounts_receivable ar;
```

### v_accounts_payable_summary

```sql
create view v_accounts_payable_summary as
select
  ap.*,
  case
    when ap.is_paid and ap.payment_date > ap.due_date then (ap.payment_date - ap.due_date)
    when not ap.is_paid and current_date > ap.due_date then (current_date - ap.due_date)
    else 0
  end as delay_days
from accounts_payable ap;
```

### v_cash_balance_by_account

```sql
create view v_cash_balance_by_account as
select
  ce.organization_id,
  ce.cash_account_id,
  sum(case when ce.entry_type = 'credit' then ce.amount else 0 end) as total_credits,
  sum(case when ce.entry_type = 'debit' then ce.amount else 0 end) as total_debits,
  sum(case when ce.entry_type = 'credit' then ce.amount else -ce.amount end) as balance
from cash_entries ce
group by ce.organization_id, ce.cash_account_id;
```

## Transactional Service Layer

The web rewrite should implement the following operations as first-class application services.

Each service should run inside a DB transaction.

### 1. Create quotation

Input:

- quotation header
- quotation items

Steps:

1. validate customer and vendor ownership
2. validate product ownership
3. calculate item totals
4. calculate quotation totals
5. insert quotation
6. insert quotation items
7. update `item_count` and `total_amount`

### 2. Convert quotation to sale

Input:

- `quotation_id`

Steps:

1. lock quotation row
2. ensure quotation is not already converted/canceled
3. create sale header from quotation
4. copy quotation items to sale items
5. calculate sale totals
6. mark quotation as `converted`
7. save `converted_sale_id`

### 3. Complete sale

This replaces the legacy stock-posting behavior.

Input:

- `sale_id`

Steps:

1. lock sale row
2. ensure sale is not canceled
3. ensure stock has not already been posted
4. load sale items
5. if `sale_requires_stock = true`, validate each product has enough stock
6. decrement `products.current_stock`
7. mark sale:
   - `status = 'posted'`
   - `is_stock_posted = true`
8. if fully settled already, also mark completed
9. write audit event

Important:

- stock posting must be idempotent
- never decrement stock twice for the same sale

### 4. Reopen sale

Use when reversing a posted sale before cancellation.

Input:

- `sale_id`

Steps:

1. lock sale row
2. ensure stock was posted
3. ensure policy allows reopening
4. increment stock back for each sale item
5. mark:
   - `status = 'draft'`
   - `is_stock_posted = false`
   - `is_completed = false`

### 5. Cancel sale

Recommended modern behavior:

- keep records
- mark canceled
- if stock was posted, either require explicit reopen first or automatically reverse within the same transaction

Preferred implementation:

1. lock sale row
2. if posted, reverse stock
3. void or reverse related financial effects
4. mark:
   - `status = 'canceled'`
   - `is_canceled = true`
   - `canceled_at = now()`

Important note:

Unlike the Firebird procedure, do not hard-delete related receipts or receivables by default.

### 6. Receive sale payment

Input:

- `sale_id`
- `receipt_date`
- `settlement_method`
- `amount_received`
- optional `cash_account_id`

Steps:

1. lock sale row
2. compute remaining amount from prior receipts
3. reject overpayment unless explicitly allowed
4. insert `sale_receipts`
5. create matching `cash_entries` credit if applicable
6. optionally update/create `accounts_receivable`
7. if remaining becomes zero:
   - `is_completed = true`
   - `status = 'completed'`
   - `completed_at = now()`

### 7. Create manual receivable

Input:

- customer
- due date
- amount
- interest rate
- description

Steps:

1. insert `accounts_receivable`
2. mark `is_open = true`
3. no cash entry yet

### 8. Settle receivable

Input:

- receivable id
- payment amount
- interest received
- discount
- payment date
- cash account

Steps:

1. lock receivable row
2. compute current due amount
3. update received columns
4. create cash credit entry
5. if fully settled:
   - `is_received = true`
   - `is_open = false`
   - `receipt_date = payment date`

### 9. Create purchase

Input:

- purchase header
- purchase items

Steps:

1. validate supplier and product ownership
2. calculate totals
3. insert purchase
4. insert purchase items

### 10. Complete purchase

Input:

- `purchase_id`

Steps:

1. lock purchase row
2. ensure purchase not canceled
3. ensure stock not already posted
4. for each purchase item:
   - increment stock
   - update product price snapshots if business rule allows
   - optionally update main supplier
   - set received quantity/date
5. mark:
   - `status = 'posted'`
   - `is_stock_posted = true`
6. write audit event

### 11. Reopen purchase

Input:

- `purchase_id`

Steps:

1. lock purchase row
2. ensure stock was posted
3. decrement product stock using purchase items
4. mark:
   - `status = 'draft'`
   - `is_stock_posted = false`
   - `is_completed = false`

### 12. Record purchase payment

Input:

- purchase id
- payment date
- method
- amount
- cash account

Steps:

1. lock purchase row
2. compute remaining amount from prior payments
3. insert `purchase_payments`
4. create matching cash debit entry
5. if fully paid:
   - mark purchase completed

### 13. Create manual payable

Input:

- supplier
- due date
- amount
- interest rate
- description

Steps:

1. insert `accounts_payable`
2. mark `is_open = true`

### 14. Pay payable

Input:

- payable id
- payment amount
- interest paid
- discount
- payment date
- cash account

Steps:

1. lock payable row
2. compute current due amount
3. update paid columns
4. create cash debit entry
5. if fully settled:
   - `is_paid = true`
   - `is_open = false`
   - `payment_date = given date`

### 15. Create manual cash entry

Input:

- cash account
- date
- credit/debit
- amount
- description
- document number

Steps:

1. validate account ownership
2. insert `cash_entries`
3. write audit event

### 16. Activate promotion

Input:

- product id
- promotional price
- dates

Steps:

1. lock product row
2. deactivate any prior active promotion for that product
3. create promotion row
4. update product:
   - `promo_price`
   - `is_promo_active = true`

### 17. Deactivate promotion

Input:

- promotion id

Steps:

1. lock promotion row
2. mark promotion inactive
3. if no other active promotion exists for the product:
   - set `products.promo_price = null`
   - set `products.is_promo_active = false`

### 18. Register inventory loss

Input:

- product id
- quantity
- date
- reason

Steps:

1. lock product row
2. validate sufficient stock if policy requires
3. insert `inventory_losses`
4. decrement product stock

### 19. Update or delete inventory loss

Because stock is affected, these must be transactional and explicit.

Update:

1. lock loss row
2. restore old quantity to stock
3. apply new quantity
4. update loss row

Delete:

1. lock loss row
2. restore quantity to stock
3. delete or archive loss row

## Integrity Rules

These invariants should be enforced in application code and, where possible, with constraints.

### Ownership

Every referenced row must belong to the same `organization_id`.

Examples:

- sale cannot use customer from another organization
- purchase cannot use supplier from another organization
- sale item cannot use product from another organization

This is a major rule. The database foreign keys alone do not guarantee it.

### Money values

All money values must be non-negative unless a future explicit credit-note design is introduced.

### Stock posting idempotence

Sale or purchase stock movement must never apply twice for the same record.

### Settlement boundaries

Do not allow:

- receivable settlement greater than total due, unless surplus handling is explicitly supported
- payable payment greater than total due, unless overpayment handling is explicitly supported

### Canceled records

Canceled sales/purchases should not accept new operational mutations unless explicitly reopened.
